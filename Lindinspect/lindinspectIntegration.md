
# 🧩 Lindinspect Integration – Node-RED Template 

## Overview

This repository provides a **fully implemented Node-RED integration** for **Lindinspect** and similar control systems.  
It adheres to Propvalue’s standards for publicly shared integration templates and includes all essential building blocks for scalable, consistent data integration.

The package enables users to:
- Retrieve, normalize, and persist all available datapoints (**Gross List**)
- Define a user-managed streaming subset (**Net List**)
- Poll and transform live time-series data with configurable intervals
- Apply robust data guards (Change/Keepalive and Time-Gate)
- Forward normalized telemetry to any downstream system

Each component is modular, documented, and reusable 

---

## ⚙️ Architecture Summary

| Flow Name | Description |
|------------|--------------|
| **Build Gross List** | Retrieves all datapoints via `/nodes` and `/leaves`, normalizes them, normalizes API-provided units, and computes deterministic HASH identifiers. |
| **Send Metadata (Gross List)** | Sends metadata for all points stored in the Gross List. |
| **Send Metadata (Net List)** | Sends metadata for only those points where `toStream: true` in the Net List. |
| **Post Time-Series Data** | Polls live values, enriches with metadata, applies filters, and emits standardized telemetry. |

> **Note:** There is **no bundled “Build Credentials” flow**. The integration **expects** a `global.config` object to already exist in persistent context. See the **Configuration** section below for how to create it.

## 🔐 Configuration – *Provide `global.config`*

### Purpose
All flows read connection and runtime settings from `global.config` in **persistent** context. You must create this object yourself before running the integration.

### Required Structure
```json
{
  "scheme": "http",
  "host": "localhost",
  "port": 8080,
  "user": "apiuser",
  "pass": "secret",
  "JOB_UUID": "job1",
  "property": "prop1",
  "deviceId": "edge-site-01",
  "pollingInterval": 60000,
  "baseUrl": "http://localhost:8080/api/v1"
}
```

### How to set `global.config`
**Option A — One‑shot Inject + Function (recommended in Node‑RED editor):**
1. Add an **Inject** node (any payload), wire it to a **Function** node.
2. Paste this code in the Function node, edit values, then click the Inject button once:
```javascript
const cfg = {
  scheme: "http",
  host: "10.0.0.1",
  port: 8443,
  user: "apiuser",
  pass: "secret",
  JOB_UUID: "c7d2c8e5-4c56-4c13-8a2d-1f8cfb458a63",
  property: 7665,
  deviceId: "edge-01",
  pollingInterval: 60000,              // ms or seconds; scheduler auto-detects
  baseUrl: "http://10.0.0.1:8443/api/v1"
};
global.set("config", cfg, "persistent");
msg.payload = { ok: true, saved: cfg };
return msg;
```
> The poll scheduler accepts milliseconds or seconds (≤ 10,000 interpreted as seconds) and normalizes internally.

**Option B — Preload via context storage file:**  
If you use file-based contextStorage, you can preseed `global.config` by writing the JSON to the appropriate storage file and restarting Node‑RED.

**Security Note:** Keep credentials in a secure store. For production, consider using environment variables and a small bootstrap Function node that assembles `global.config` from `env`.

## 🧱 Gross List Flow

Builds the **Gross List** by reading the full hierarchy of nodes and leaves from the Lindinspect API, normalizing fields and **using the unit provided by the API** as the source of truth (with normalization of aliases, no subject‑based inference).

### Process
1. Authenticate using values from `global.config`.  
2. Fetch `/nodes` and `/nodes/{id}/leaves` with jitter/rate‑limit to avoid bursts.  
3. Normalize datapoints:
   - Canonical subject names
   - **Unit normalization from `leaf.unit`** (e.g., °C, l/s, Pa, %, W, V, ppm, min, s, hrs)
   - Extracted context (system, component, room)
4. Compute deterministic `HASH` per datapoint:  
   `HASH = sha256(property + '|' + lindinspectid + '|' + description)`  
5. Persist the list under `global.genericGrossList` and mirror it to `global.genericNetList` (editable).

### Diagnostics
- Duplicate HASH detection (per property)  
- Label collision analysis (I/O and Orbiq labels)  
- Persisted timestamp for last rebuild

## 🧩 Net List (User‑Managed Subset)

The **Net List** defines the points to be streamed in real time. The **Net List** is not generated by this integration.
It is entirely the user’s responsibility to create, manage, and maintain the Net List externally.

Each record contains a Boolean flag:
```json
"toStream": true
```

### Management Options
- Manually through Node‑RED Context Explorer  
- Import/export via CSV  
- Remote synchronization through an HTTP endpoint

> The Net List is **not auto‑generated**. Users must define or maintain it explicitly.

## 🧾 Metadata Flows

### Gross List Metadata Flow

- Reads from `global.genericGrossList`  
- Deep-clones the payload to prevent downstream mutation  
- Creates and updates **complete metadata objects**, for example:

```json
{
  "label": "LB11-TD11:5-1114_RoomTemperature",
  "description": "Room temperature",
  "unit": "°C",
  "writable": false,
  "source": "prop1_LINDINSPECT",
  "property": "prop1",
  "floor": 1,
  "zone": "",
  "room": 1114,
  "system": "LB11",
  "component": "TD11:5",
  "system_id": "prop1_LB11",
  "component_id": "prop1_LB11_TD11:5",
  "lindinspectid": 11005,
  "leafId": "9070",
  "HASH": "d2aea336"
}
```

### Net List Metadata Flow
- Reads from `global.genericNetList`  
- Emits metadata for all points where `toStream: true`

Attach any Node‑RED output node (HTTP Request, MQTT Out, Database, etc.) to forward metadata externally.

## ⏱️ Time‑Series Polling Flow

Handles all live data polling and streaming operations.

### Key Components
1. **Poll Scheduler** – Emits ticks at intervals defined by `global.config.pollingInterval` (seconds → ms auto‑handled).  
2. **BuildPairsFromInventory** – Extracts `(nodeId, leafId)` pairs from Net List where `toStream: true`.  
3. **BuildRequest** – Constructs authenticated GETs: `GET {baseUrl}/nodes/{nodeId}/leaves/{leafId}/value`.  
4. **ShapeResult** – Normalizes API response to `{ value, at, nodeId, leafId }`.  
5. **Enrich → Telemetry Envelope** – Adds metadata fields and standardizes timestamps (UTC ISO‑8601).  
6. **Time‑Gate Filter** – Rejects outdated or replayed records.  
7. **Change/Keepalive Filter** – Emits only changed or periodic values.  
8. **Output Counters & Debug** – Tracks throughput and outputs telemetry.

### Standardized Telemetry Schema
```json
{
  "job_uuid": "c7d2c8e5-4c56-4c13-8a2d-1f8cfb458a63",
  "sourceLabel": "Server_Rumstemperatur_101",
  "dataType": "Double",
  "time": "2025-11-11T08:30:00Z",
  "value": 22.3,
  "hash": "1e0a…",
  "timestamp": "2025-11-11T08:30:00Z"
}
```
All timestamps are generated in **UTC (ISO‑8601)** directly in Node‑RED.

## 🔁 Filters and Guards

### Change / Keepalive Filter
- Emits a record when the value changes or when the last update exceeds the keepalive timeout (default: 5 minutes).  
- Maintains state per `HASH` in persistent context for durability across restarts.

### Time‑Gate Filter
- Prevents replay or out‑of‑order data delivery.  
- Uses compact rolling arrays to track the most recent timestamps per `HASH`.  
- Automatically compacts stored state to maintain low memory usage.

## 🧮 Data Normalization Rules

| Field | Description | Source |
|--------|--------------|--------|
| `label` | Node label combined with subject | API |
| `description` | Original leaf name | API |
| `unit` | **Normalized unit (from API)** | API |
| `property` | Property or site ID | Config |
| `source` | Composite source ID | Derived |
| `lindinspectid` | Node ID | API |
| `leafId` | Leaf ID | API |
| `HASH` | Deterministic ID | `sha256(property | lindinspectid | description)` |
| `toStream` | Streaming flag | Boolean |

## 🚀 Deployment Steps

### 1. Prepare the Configuration  
Before importing any flows, create and persist the `global.config` object as described in the **Configuration** section.  
Make sure:
- **Persistent context** is enabled in Node-RED (`settings.js → contextStorage`).  
- The configuration includes valid Lindinspect credentials, property ID, and polling interval.  
- The `baseUrl` points to your Lindinspect API endpoint (including `/api/v1`).  

You can create it with an **Inject + Function** node or pre-seed it via context storage.

---

### 2. Import the Node-RED Flows  
Import all JSON flow files included with this integration into your Node-RED workspace.  
Recommended order:
1. **Build Gross List**  
2. **Send Metadata (Gross List)**  
3. **Send Metadata (Net List)**  
4. **Post Time-Series Data**

These flows are modular — you can import only the ones you need, but **Build Gross List** is required for initialization.

---

### 3. Deploy the Flows  
Click **Deploy** in Node-RED to load and activate all nodes.  
After deployment, the integration will read `global.config` and prepare the internal state automatically.

---

### 4. Build the Gross List  
Manually trigger the **Build Gross List** flow once after deployment.  
This will:
- Fetch all nodes and leaves from the Lindinspect API  
- Normalize and store them under `global.genericGrossList`  
- Generate deterministic HASH identifiers for each datapoint  

You can re-run this manually at any time or schedule it using a Cron trigger.

---

### 5. Provide the Net List  
Since the Net List is **not created automatically**, you must provide it manually.  
You can:
- Create it directly in Node-RED (`global.genericNetList`)  
- Import it from a JSON/CSV file containing datapoints with `toStream: true`  
- Populate it through an external service via the Node-RED context API  

Only points with `toStream: true` will be polled and streamed.

> The template never generates, or updates the Net List.  
> It is fully user-managed and must be maintained externally.

---

### 6. Attach Output Nodes  
Connect your preferred downstream transport nodes after the metadata and telemetry outputs.  
Supported options include:
- **HTTP Request** → send data to REST endpoints  
- **MQTT Out** → publish to message brokers  
- **Database nodes** → InfluxDB, SQL, etc.  
- **File Writer / CSV** → local or edge storage  

---

### 7. Verify and Monitor  
After setup:
- Confirm that **Gross List** and **Net List** objects exist in persistent context.  
- Check the debug output for successful polling and telemetry messages.  
- Validate timestamps, HASH uniqueness, and expected data volume.

---

### Runtime Behavior Summary  
Once deployed and configured:
- The Gross List is built and stored persistently.  
- The Net List (provided by the user) defines which points are streamed.  
- Polling begins automatically at the configured interval.  
- Normalized telemetry is emitted through the connected output nodes.


## 🧩 Troubleshooting

| Symptom | Likely Cause | Recommended Action |
|----------|---------------|--------------------|
| No telemetry emitted | Missing or empty Net List | Ensure `toStream: true` for required points |
| “Invalid time” errors | Malformed timestamps | Verify UTC ISO‑8601 formatting |
| Memory pressure | Excessive parallel requests | Adjust rate limits or introduce batching |
| Duplicate values | HASH collision detected | Run diagnostic node and resolve conflicts |
